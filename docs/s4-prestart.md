# Codex 새 ID 복원과 보호 엔진

이 문서는 S4 개발 중의 구현 경계를 설명합니다. 현재 보호 엔진의 활성화·실제 복원 시험과 최종 독립 감사는 끝나지 않았습니다. 실행 파일 해시가 확정되지 않은 빌드는 패키지 생성과 실행을 차단합니다.

## 복원 경로

`CodexDesktop.ps1`는 미리보기에서 `bin/ctxhop-codex.exe plan`을 호출합니다. Go 구현은 새 ID 복원, 기존 ID, 지원하지 않는 백업, 차단을 구분합니다. 기존 ID와 명시적인 지원 제외만 기존 Python 검사로 넘깁니다. Go 오류·차단·잘못된 응답은 Python 복원으로 우회하지 않습니다. 미리보기 영수증에 선택한 경로와 백업·홈·작업 폴더·토큰을 함께 고정하고 복원에서도 그 경로를 사용합니다.

Go 구현은 표준 라이브러리와 Windows의 `winsqlite3.dll`을 사용합니다. 직접 SQL 쓰기를 하지 않습니다. DB 구조와 실제 멤버·참조 관계를 읽어 안전 조건을 확인하고, 승인된 엔진 메서드로 새 ID를 등록합니다. 백업 원본 대화 파일은 바꾸지 않습니다. 새 복원에서는 이 PC의 작업 폴더와 `untrusted` 승인 정책·읽기 전용 권한을 적용하고, 구성원별 첫 재개와 새 엔진의 후속 재개에서 결과를 확인합니다. 같은 ID의 대화가 있으면 이 경로에서 덮어쓰지 않습니다.

파일 배치 이후 실패하면 복구 기록을 남깁니다. 대화를 자동 삭제하지 않습니다. 사용자가 복구를 선택하면 새 설정·DB·파일·엔진 확인을 거친 뒤 해당 작업의 범위만 되돌립니다. 삭제 범위를 증명하지 못하거나 관계없는 참조가 있으면 `needs_attention`으로 남깁니다.

## 시작 전 설정 확정

보호 엔진은 공식 Codex 소스의 설정·인증·관리 정책 로더와 DB 행 해석을 재사용합니다. 임의로 TOML 일부를 읽어 정상 엔진 설정이라고 추정하지 않습니다. 같은 프로세스에서 준비한 객체를 활성화에 사용하며, 변경된 입력·잘못된 결합·재사용 요청은 거절합니다. 보호 엔진은 일반 Codex CLI 실행 경로를 사용하지 않습니다.

준비 결과에는 실제 SQLite 홈과 쓰기 대상, 구성원별 작업 폴더와 설정 결합을 포함합니다. 인증 정보와 원문 설정은 반환하지 않습니다. 시작 전 DB 열기·인증 갱신·배경 플러그인 및 네트워크 동작을 막는 경계와, 활성화 뒤 허용할 메서드를 별도로 검증합니다. 프로세스가 보고한 `effects=0`만으로 무쓰기·무네트워크를 증명하지 않습니다.

`CODEX_SQLITE_HOME`이 존재하거나 루트 설정에서 SQLite 경로를 바꾸면 값이 같은 경로여도 차단합니다. 알려지지 않은 DB 구조, 실제 설정을 확정하지 못한 인증·정책, 승인하지 않은 구성원과 쓰기 대상도 차단합니다. 프로젝트 설정이 적용된 경로는 미리보기에서 알립니다.

WAL 모드 DB는 읽기 전용 연결도 파일을 생성할 수 있습니다. 원본을 raw 읽기 핸들로 확인하고 현재 사용자만 접근할 수 있는 새 사본에서 Go와 보호 엔진이 같은 DB 세대를 읽는 경로를 연결하고 있습니다. 사본은 준비 단계의 조회에만 쓰며 실제 복원 설정은 원래 DB를 가리킵니다. 원본 main·WAL·SHM을 바꾸지 않고, 사본의 sidecar 생성과 정리를 따로 확인합니다. 현재 생산 경로는 검증 전까지 WAL 부재를 차단합니다. 이 격리 시험을 전체 기존 홈 지원 완료로 해석하면 안 됩니다.

정상 앱·CLI·IDE와 DB writer를 닫은 상태를 운영 조건으로 유지합니다. 검사 핸들을 해제한 뒤 설정·파일·DB와 프로세스를 다시 확인하고 복원을 시작합니다. 해제부터 첫 쓰기까지 경쟁 구간이 남으므로 모든 미래 writer를 원자적으로 막는다고 보장하지 않습니다.

## 실행 파일과 소스 결합

`engine/provider.json`은 공식 소스 commit, 검토한 패치와 SHA-256, Rust 버전, Windows 대상, loader 계약 ID, 보호 엔진 및 정상 설치 엔진 SHA-256을 지정합니다. Go 실행 파일에는 두 엔진 SHA-256과 계약 ID를 빌드 시 넣고 PowerShell 구현은 Go 실행 파일의 SHA-256을 고정합니다. 어느 핀도 비어 있으면 실행할 수 없습니다. 숫자 버전 비교만으로 새 엔진을 허용하지 않습니다.

정상 설치 엔진은 해시와 파일 identity만 읽습니다. 도움말이나 버전을 얻기 위해 실행하지 않습니다. 엔진 파일과 경로를 유지한 상태에서 보호 엔진을 suspended 상태로 만들고, 소유 Job에 넣은 뒤 실행합니다. 종료 때 자손까지 active process 수가 0이어야 다음 단계로 갑니다. 이 기능은 사용자 앱을 종료하지 않습니다.

새 정상 엔진을 지원할 때는 공식 소스·설치 바이너리 대응, canonical 로더 및 복원 API 의미, 효과 경계와 격리 시험을 확인하고 provider 핀을 갱신해야 합니다. 확인하지 않은 새 실행 파일은 쓰기 전에 멈춥니다.

## 빌드와 검증

`build/build-codex-engine.ps1`은 고정 공식 소스의 LF archive에 검토한 패치를 적용해 `ctxhop-codex-engine.exe`를 만듭니다. Windows 정상 DB의 sqlx 체크섬과 호환되도록 canonical SQL 마이그레이션만 CRLF로 변환합니다. 빌드 영수증에 변환 전후 SHA-256과 sqlx SHA-384를 기록하며 기존 DB의 체크섬 검사를 완화하지 않습니다. 실행 파일을 실행하지 않습니다. Rust 1.95.0과 Windows MSVC/SDK 환경이 필요합니다. `build/build-exes.ps1`은 보호 엔진과 Go 구현을 빌드하고 모든 실행 파일의 핀을 검사합니다. `build/build.ps1`은 커밋된 파일만 패키지에 넣습니다.

`impl/codex/Run-Fixtures.ps1`의 Go 시험은 자체 mock 엔진, 실제 Windows Job·이미지 핸들·읽기 전용 SQLite 및 guard 거절을 구분해 기록합니다. 핀이 없는 시험 빌드는 실제 보호 엔진 복원의 증거가 아닙니다. `Test-DesktopWorker.ps1`은 PowerShell 경로 고정과 실패·복구 연결을 검사합니다. `Test-PrestartEngine.ps1`은 별도 fixture 준비·관측을 담당하며 실제 엔진 수용 결과를 자체 검사와 분리합니다.

릴리스 수용에는 최종 고정 소스와 바이너리, 실제 보호 엔진의 legacy/paginated·부모/자식·보관 상태·전체 이력·설정 시험, 실패 후 수동 복구, 효과 관측과 독립 감사가 모두 필요합니다. 실행하지 않은 시험은 성공으로 기록하지 않습니다.
